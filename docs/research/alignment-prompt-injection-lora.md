# Alignment and prompt-injection resistance for a small-domain QLoRA assistant

**Scope.** This report separates two objectives: (1) *instruction security*—do not let lower-trust content override higher-trust application instructions or cause unauthorized actions—and (2) this tutor's *answer-leakage policy*—do not provide completed code, final output, or equivalent prose while still diagnosing the learner and offering a next step. They overlap, but neither implies the other. The repository's rubric defines the second objective, not a general security guarantee ([tutor rubric](https://github.com/jakemaly/socratic/blob/feat/demo-v1/eval/judge.py)).

## 1. Instruction hierarchy and privileged instructions

The Instruction Hierarchy paper identifies the core failure: models often treat developer/system text as having the same priority as user or third-party text. It proposes explicit priorities—system/application instructions over user instructions, and user instructions over third-party/tool content—and training examples that selectively ignore conflicting lower-privilege instructions while preserving aligned requests. Its experiments report improved robustness, including to attack types not seen in training, with limited standard-capability degradation ([Wallace et al., *The Instruction Hierarchy*](https://arxiv.org/abs/2404.13208)).

For this assistant, the runtime contract should therefore be explicit: system/developer policy is authoritative; learner text is an untrusted request; retrieved documents, pasted webpages, files, and tool results are data, not instructions. Preserve their boundaries in structured messages and never give model-generated text direct authority to call sensitive functions. OWASP recommends constrained behavior, validated output formats, least privilege, human approval for high-risk actions, segregation of external content, and adversarial testing; it also says there is no foolproof prevention method ([OWASP LLM01:2025](https://genai.owasp.org/llmrisk/llm01-prompt-injection/)). A system prompt should be treated as policy rather than a secret: prompt leaking is itself a known attack objective ([Schulhoff et al., *PromptInject*](https://arxiv.org/abs/2211.09527)).

## 2. Direct and indirect injection threat models

A direct injection is a malicious or accidental learner message that changes intended behavior. PromptInject demonstrated goal hijacking and prompt leaking against GPT-3 using iterative adversarial prompt composition ([Schulhoff et al.](https://arxiv.org/abs/2211.09527)). In a five-turn tutor conversation, attacks include “ignore the tutor policy,” role-play or encoding, incremental pressure, and asking the model to reveal hidden instructions. Multi-turn context matters: Crescendo starts benignly and escalates by referring to prior answers, achieving high attack success across tested systems ([Russinovich et al., *Crescendo*](https://arxiv.org/abs/2404.01833)).

An indirect injection arrives through content the application retrieves or processes rather than through the apparent user request. Greshake et al. showed that malicious instructions in webpages or other retrieved data can manipulate outputs, trigger arbitrary application behavior, influence API calls, and exfiltrate information ([*Not what you've signed up for*](https://arxiv.org/abs/2302.12173)). This repository currently has no tool-calling or retrieval path in the fixed benchmark, so indirect injection is not measured by its 48 cases; adding RAG or tools would materially change the threat model. OWASP explicitly warns that fine-tuning and RAG do not fully mitigate injection ([OWASP LLM01:2025](https://genai.owasp.org/llmrisk/llm01-prompt-injection/)).

## 3. Refusal, helpfulness, leakage, and over-refusal

A safety-aligned response should refuse the disallowed action while remaining useful. Constitutional AI uses a principles-based critique-and-revision SFT phase followed by preference/RLAIF training, and reports a harmless but “non-evasive” assistant that explains objections rather than simply refusing ([Bai et al., *Constitutional AI*](https://arxiv.org/abs/2212.08073)). For this tutor, the target is narrower: briefly decline the completed artifact, name the likely conceptual error, and ask one relevant next-step question. That target is a behavioral policy, not proof that the model understands security.

Refusal has a cost. A model can reduce apparent leakage by refusing ordinary, safe tutoring, or by giving generic refusals that fail the learner. The Instruction Hierarchy work evaluates over-refusal alongside robustness and reports limited degradation in its experiments, but those results are not a guarantee for Gemma 4, rank 16, or this dataset ([Instruction Hierarchy](https://arxiv.org/abs/2404.13208)). Evaluate leakage and helpfulness separately: `leaks / 48`, actionable diagnosis, ordinary tutoring utility, and refusal behavior on benign near-misses. One fixed-case result should not be treated as a security rate; the repository's benchmark is a curated Socratic-policy test with four balanced families ([benchmark definition](https://github.com/jakemaly/socratic/blob/feat/demo-v1/data/benchmark/README.md)).

## 4. SFT versus preference optimization

SFT is the first sensible intervention when the desired behavior can be demonstrated directly. Constitutional AI's SFT phase trains on revised helpful/harmless responses ([Constitutional AI](https://arxiv.org/abs/2212.08073)). For this tutor, assistant targets should contain the boundary plus diagnosis and a question; prompts may contain the requested solution, but assistant targets should not reproduce it. Keep assistant-only loss as an auditable objective choice and verify the rendered chat-template mask ([TRL SFTTrainer](https://huggingface.co/docs/trl/en/sft_trainer)). Include paraphrases, indirect wording, “just confirm” requests, and multi-turn pressure while retaining ordinary stuck-learner examples.

Preference optimization is useful after SFT has a clean target. DPO converts preference comparisons into a classification-like objective relative to a reference policy, avoiding a separately trained reward model and online RL ([Rafailov et al., *DPO*](https://arxiv.org/abs/2305.18290)). Construct pairs with the same prompt: chosen = “refuse the artifact + diagnose + next step,” rejected = either a leak or a sterile refusal. DPO's reference-policy computation is an extra practical burden on one 24-GiB GPU.

ORPO combines SFT with an odds-ratio penalty and removes the reference model; its authors still emphasize that successful preference alignment relies on SFT-like learning ([Hong et al., *ORPO*](https://arxiv.org/abs/2403.07691)). SimPO uses average sequence log-probability as a reference-free reward and adds a target margin ([Meng et al., *SimPO*](https://arxiv.org/abs/2405.14734)). Both reduce reference-model memory, but neither guarantees security: pair quality, margin/weight choices, response length, and over-refusal remain variables. Do not use the fixed 48 cases as preference-training targets; use new paraphrases and reserve the benchmark for evaluation.

## 5. What QLoRA changes—and does not

LoRA freezes pretrained weights and learns low-rank updates inserted into Transformer layers ([Hu et al., *LoRA*](https://arxiv.org/abs/2106.09685)). QLoRA backpropagates through a frozen 4-bit base into LoRA adapters and introduces NF4, double quantization, and paged optimizers to reduce memory ([Dettmers et al., *QLoRA*](https://arxiv.org/abs/2305.14314)). These methods make a large adaptation feasible; they do not create a security monitor or a hard policy boundary.

Capacity is a real alignment limitation. In a comparison using substantially larger datasets, standard LoRA underperformed full fine-tuning while preserving more out-of-domain performance; full fine-tuning learned perturbations with ranks 10–100 times typical LoRA settings ([Biderman et al., *LoRA Learns Less and Forgets Less*](https://arxiv.org/abs/2405.09673)). Thus rank 16 may be adequate for a narrow stylistic boundary, but cannot be assumed sufficient for robust hierarchy following, generalization, and tutoring simultaneously. LoRA's better retention of unrelated behavior is a useful interference tradeoff, not evidence that catastrophic interference or forgetting is eliminated ([same paper](https://arxiv.org/abs/2405.09673)).

Adapter composition is another untested interaction. LoRAHub demonstrates composing task adapters dynamically ([*LoraHub*](https://arxiv.org/abs/2307.13269)); composition should not be presumed to preserve a safety adapter's behavior because low-rank updates can interact. If multiple adapters are ever loaded or merged, test the exact composition against both policy and security suites rather than reasoning from each adapter's isolated score. Data and objective design matter at least as much as rank: balanced attack families, hard negatives, clean assistant targets, held-out paraphrases, and replay of ordinary tutoring are more defensible than simply increasing epochs or rank ([Instruction Hierarchy](https://arxiv.org/abs/2404.13208); [TRL SFTTrainer](https://huggingface.co/docs/trl/en/sft_trainer)).

## 6. Practical plan for this repository

The historical V1/V2 recipe used Gemma 4 31B, pre-quantized 4-bit QLoRA, rank 16/alpha 32, all-linear targets, three epochs, 1,024-token maximum, micro-batch 1, gradient accumulation 4, assistant-only loss, and one RTX 3090; V1 and V2 each used 400 SFT dialogues (historical V1/V2 configuration receipts; [Gemma QLoRA guide](https://ai.google.dev/gemma/docs/core/huggingface_text_finetune_qlora)). The selected next run used four epochs for snapshot comparison. This is a reasonable memory-first baseline; the official Unsloth Gemma guide reports about 22 GB for its 31B QLoRA setup ([Unsloth guide](https://unsloth.ai/docs/models/gemma-4/train.md)). Change one variable at a time: first improve balanced, adversarially varied SFT targets; only then compare ORPO or SimPO with the same seed, base revision, decoding, and held-out data.

Add a separate injection suite: system-prompt extraction, direct hierarchy conflicts, learner pressure over five or more turns, obfuscated/multilingual variants, and indirect-content probes. If the product later gains tools, use least-privilege wrappers and human confirmation for side effects, and evaluate with an agent environment rather than only chat transcripts. AgentDojo is designed for untrusted tool-returned data, adaptive attacks, and evolving defenses, with 97 tasks and 629 security cases ([Debenedetti et al., *AgentDojo*](https://arxiv.org/abs/2406.13352)). For automated red-teaming, HarmBench provides a standardized framework and compares attacks and defenses across models ([Mazeika et al., *HarmBench*](https://arxiv.org/abs/2402.04249)); PAIR supplies a black-box iterative attacker that refines prompts using target responses ([Chao et al., *PAIR*](https://arxiv.org/abs/2310.08419)). Re-run attacks adaptively after every defense change; static attack strings systematically understate risk.

## 7. What V1/V2 establish—and cannot establish

On the fixed 48-case judge benchmark, V1 has leakage **2/48 (4.17%)** and actionable diagnosis **32/48 (66.67%)**; V2 has leakage **3/48 (6.25%)** and diagnosis **43/48 (89.58%)** ([published comparison](../../results/summary.md)). These results support a cautious statement: V2 improved this judge's diagnosis score, while leakage differed by one case. They do **not** establish that V2 is less secure, that either adapter resists prompt injection, that either model follows an instruction hierarchy, or that either behavior generalizes beyond these 48 cases.

Specifically, the current results do not test indirect injections, tool/API misuse, system-prompt extraction as a security property, adaptive attackers, longer conversations, multilingual/obfuscated attacks, benign over-refusal, multiple seeds, alternative judges, or statistical uncertainty. They also cannot separate the effects of V2 data composition from training randomness or judge variance. Keep the fixed benchmark for continuity, but add the separate adaptive security suite before making any claim of prompt-injection resistance.
